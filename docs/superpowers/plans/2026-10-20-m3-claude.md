# M3: Claude integration — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Claude can search, add and edit recipes through the MCP server, following a
style guide the server provides. A URL import stores the source link and the page's main
photo.

**Architecture:** The MCP tools are thin wrappers over the M2 store: `via="claude"`,
the same drafts, the same timeline. Edits carry the version Claude read, and the store
refuses an edit whose base is stale. Claude is now a second writer next to the app, so the
app's editor sends its base version too. One new module, `recipes/fetch.py`, does the only
outbound HTTP. It fetches the source page's `og:image` and any `image_url` Claude passes,
and refuses private addresses. The style guide is package data (`src/app/style_guide.md`)
and the server offers it three ways: as a tool, a resource and a prompt.

**Tech Stack:** as M2. `httpx2` (already installed as a dependency of `mcp`) becomes a
direct runtime dependency for the fetcher. HTML is parsed with the standard library's
`html.parser`. No other new dependencies.

**Spec:** `docs/plan.md` (M3, Open questions), `docs/requirements-v1.md` (7, 8, 10,
24–26, the two open questions on photos and licensing), `CLAUDE.md`, and the style guide
draft `src/app/style_guide.md`. The rulings below settle what those leave open.

## Rulings (for Serwan to confirm at review)

1. **Image licensing (confirmed by Serwan, 2026-10-20: liberal).** The app is only for
   Serwan and his partner, behind Cloudflare Access, so no photo is ever republished.
   A URL import keeps the source site's own photo, with the source link stored next to
   it. A recipe with no source may get an `image_url` of any photo on the web that shows
   the dish well; no licence check. The server cannot check licences and does not try.
   An illustration fallback stays after the PoC.
2. **Chat-attached photos.** An MCP tool receives JSON arguments only, so Claude can read
   a photo in the chat but cannot hand its bytes to the server. There is no upload tool.
   Claude transcribes the recipe, and the photo is added with the app's upload button.
   The style guide says so.
3. **Style guide location.** `src/app/style_guide.md`, not `docs/style-guide.md`: `docs/`
   is not in the image, and the server must read the file at runtime. `docs/plan.md`
   points to it.
4. **Edits are checked against a version.** `edit_recipe` requires the `version` from
   `read_recipe`. The store refuses an edit whose version is stale (`VersionConflict`), and
   the app's editor sends `base_version` too. This is the M2 minor finding "no
   concurrency check", which matters now that two writers exist. A recipe's version is
   `current_version or 0`.
5. **What Claude can't do in M3:** set marks or ratings, add notes or "Made it", delete,
   restore, or edit the catalog's g-per-tsp. The tools don't offer these. Merge and
   inventory tools are after the PoC.
6. **Duplicate imports.** `add_recipe` refuses a `source_url` that a recipe on the same
   side already has. The refusal names the slug and points to `edit_recipe`, so a retried
   tool call can't create a second copy.
7. **Photo failures never block a save.** A failed `og:image` or `image_url` becomes a
   sentence in the result's `warnings`, and the recipe is saved without a photo.

## Global Constraints

- Writes only to `/data` (through `RecipeStore` and `UploadStore`) and `/tmp`. No new
  settings and no secrets: `nas-app.toml` and `config.example.toml` are unchanged.
- Every MCP write uses `via="claude"`. Every refusal is a `ToolError` with one plain
  sentence, the same sentences the app shows where one exists.
- Outbound HTTP only through `Fetcher`. Only `http` and `https`, ports 80 and 443 (or
  none given), no credentials in the URL. Every host must resolve only to global unicast
  addresses (`ipaddress.ip_address(a).is_global and not .is_multicast`), checked before
  the first request and again before each redirect hop. At most 3 redirects. Each request
  has a 10 s timeout and each fetch a 15 s total deadline. Pages are cut off at 2 MiB,
  images at `MAX_UPLOAD_BYTES` (20 MB), with the body streamed and the fetch stopped
  early. `trust_env=False`. User-Agent `Mozilla/5.0 (compatible; Laekkert/1.0)`.
- Tests never touch the network: `Fetcher(transport=httpx2.MockTransport(...),
  resolve=<fake>)`.
- The fetch is async (`httpx2.AsyncClient`, `loop.getaddrinfo`). The MCP tools that use
  it are `async def`, so the event loop is never blocked.
- British spelling and sentence case in all copy. No model names in repo files.
- Full check before each commit:
  `just lint && just test && (cd web && npm test && npm run lint && npm run build)`.

## Review Focus

1. **Claude sends US units (`"cup"`, `"oz"`) or a unit-less amount.** It must get a
   refusal that says metric only and names the row, never a crash or a silent save
   (Task 5 test `test_add_recipe_refuses_cups`).
2. **The page's `og:image` is relative, protocol-relative or HTML-escaped**
   (`//cdn.x/a.jpg`, `/img/a.jpg?w=1&amp;h=2`). It must resolve against the final page URL
   after redirects (Task 2 test `test_page_image_resolves_relative`).
3. **The image URL points to an HTML page, an SVG or a 40 MB file.** The recipe is still
   saved, with a warning (Task 5 test `test_add_recipe_bad_image_still_saves`).
4. **The app's editor and Claude edit the same recipe.** The second save is refused in
   both directions, and nothing is lost silently (Task 1 API test, Task 6 MCP test).
5. **A redirect from a public host to `http://169.254.169.254/` or `http://localhost`.**
   It must be refused at the hop (Task 2 test `test_redirect_to_private_refused`).

### Task 6: `edit_recipe`

**Files:**
- Modify: `src/app/mcp_server.py`, `tests/test_mcp.py` (`test_tools_listed`)
- Test: `tests/test_mcp_writes.py`

**Interfaces:**
- Consumes: `RecipeStore.update(..., base_version=)` and `VersionConflict` (Task 1),
  `saved()` and the photo steps (Task 5).
- Produces:
  - `class RecipeChanges(BaseModel)` with `extra="forbid"`. Every field is optional:
    `name`, `category`, `servings`, `time_minutes`, `ingredients`, `steps`, `tags`,
    `source_url`. A field left out stays as it is. `time_minutes: null` clears the time,
    so the model uses `model_fields_set` to tell left out from null. A list replaces the
    whole list.
  - `async edit_recipe(side, slug, version: int, changes: RecipeChanges, image_url: str | None = None, remove_image: bool = False, ctx: Context) -> dict`.
    It returns `saved(...)`.
    - It merges the changes onto the current recipe, which gives a `RecipeDraft` with the
      current `image` and `source`.
    - `image_url` fetches and parks a new photo. A failure is a warning, and the old
      photo stays.
    - `remove_image` sets `image=None`. Passing both is a ToolError:
      `"Pass image_url or remove_image, not both"`.
  - Errors:
    - An unknown recipe → `ToolError(f"No recipe {slug!r} on the {side} side")`, as
